# GH-819: pytest, vitest and docs workers from the check share

The system's check scheduler hands each gate a core share in `CHECK_WORKERS` and
`PYTEST_XDIST_AUTO_NUM_WORKERS` (agentic-system ADR-0070, section "Trabajadores"; it also sets
`VITEST_MAX_WORKERS`). Machine: 16 cores (`nproc` 16), shared with other worktrees, so every load
is an upper bound. Each run below was started with the other share variables removed (`env -u`),
so only the named one acts.

## pytest: `-n auto` through the conftest hook

`uv run --no-project pytest -n auto -p no:cacheprovider -o addopts= tests/docs/test_tools.py`
(`-o addopts=` drops pyproject's `-q`, which hides xdist's `created:` line; a small file keeps the
run short, the hook does not depend on the selection).

| Share | Load before (`uptime`) | xdist line, verbatim |
| --- | --- | --- |
| `CHECK_WORKERS=2` only | 17.96, 21.56, 19.08 | `created: 2/2 workers` (38 passed) |
| `PYTEST_XDIST_AUTO_NUM_WORKERS=2` only | 16.74, 21.18, 18.99 | `created: 2/2 workers` (38 passed) |
| neither (16 cores, so `min(8, 16)`) | 15.39, 20.74, 18.87 | `created: 8/8 workers` (38 passed) |

The full new `tests-fast` command with `CHECK_WORKERS=2` (load before 15.47, 20.59, 18.84; only
`-o addopts=` added, to show the line):

```
created: 2/2 workers
2 workers [1197 items]
1197 passed, 8 warnings in 492.20s (0:08:12)
```

`pytest --co` starts no workers whatever `-n` says (xdist only collects), so the subprocess test in
`tests/test_check_share.py` runs a real selection (`-k positive_count`) instead.

## vitest: `maxWorkers` from `CHECK_WORKERS`

Worker processes counted every 0.5 s (descendants of the run whose command line carries
`--experimental-import-meta-resolve`, which only vitest's fork workers do), `npx vitest run
src/components` (48 files), `VITEST_MAX_WORKERS` removed:

| Share | Most workers alive at once |
| --- | --- |
| `CHECK_WORKERS=2` | 2 |
| `CHECK_WORKERS=` (empty, no share) | 15 (vitest's own default, cores - 1) |

With `VITEST_MAX_WORKERS=4` set (as the scheduler's own shell had it) and `CHECK_WORKERS=2` the
count was 4: vitest gives its own `VITEST_MAX_WORKERS` precedence over the config's `maxWorkers`.
So the scheduler's own variable wins when it sets one; `CHECK_WORKERS` is the cap when it does not.
`CHECK_WORKERS=2 npm --prefix web test` (the whole suite, that shell's `VITEST_MAX_WORKERS=4`
still set) passed: 351 files, 5572 tests, 475.93 s, at most 4 workers. A second whole-suite run
with `VITEST_MAX_WORKERS` removed was cut off by the 600 s tool timeout and not repeated; the scoped
runs above are the recorded counts.

## docs: the cap is on concurrent tool calls

`worker_count()` and `node_worker_count()` in `scripts/docs/tools.py` honour `CHECK_WORKERS`
(tests/docs/test_tools.py, `test_the_worker_caps_honour_the_check_share`). The cap is on the tool
calls `run_all` has in flight, not on processes: a tool that starts threads or children of its own
is not counted.

## Limits

- `stack.yaml` is read at a task's base, so the new `-n auto` commands apply from the next task.
  This task's green gates prove the hook and the readers, not the new commands.
- With no share, `tests-fast` can start up to 8 workers where it started 4.
- CI does not set the variables, so its parallelism is unchanged.
